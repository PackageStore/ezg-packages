Generate one UI mockup for this project. The `.ui-spec.json` is the single source of truth; HTML is generated, never hand-authored.

## Input

- `featureName`, `screenName`, `branch` (`Popup` or `FullScreen`).
- `outputPath`: `TechSpec/Mockups/<Feature>/<Screen>.html`; derive the sidecar `<Screen>.ui-spec.json`.
- Task/TechSpec paths and optional reference notes.

## Procedure

1. Read `.claude/ui-kit/ui-kit.json` and the supplied requirements. Use only kit template names. A template's `usage` note is **binding**, not commentary: it carries the composition rules the geometry cannot show (which parent a template must sit in, what it may contain).
   Then read the project's art direction, `.claude/docs/ArtStyle.md`, and `Read` the board images it lists under `.claude/docs/ArtStyle/`. The kit tells you *which* templates exist; ArtStyle tells you how the game *looks*. It is binding the same way:
   - every `color` in the spec is an ArtStyle palette token (write the hex, and name the token in `assumptions[]` when it is not obvious); every `fontSize` sits on its type table. Never invent a hex. A needed colour with no token → use the nearest token and log it in `assumptions[]`;
   - follow its layout rules (where close/back sits, popup vs full-screen, the offer-popup family) and never draft anything in its "rejected directions" section;
   - style is not a `questions[]` topic — ArtStyle answers it. Missing file or `Status: template` → draft from the kit only and record `assumptions[]: "ArtStyle.md chưa điền — màu/chữ theo kit, cần dev duyệt"`.
2. Build a v1 spec following `.claude/docs/ui-spec-schema.json`:
   - `specVersion: 1`, `designResolution` = the project's (`python3 .claude/scripts/ui_spec_common.py design-resolution` — EZG standard `[1080, 2400]`, the `screen_template` CanvasScaler; a legacy `[1080, 1920]` only warns and is never right for a new draft), and `contentRoot` (the container mirroring the template's content node — base kit: `container_content` for Popup, `content` for FullScreen). All vertical geometry is laid out on that height.
   - Mirror Unity containment. Every non-template-owned element must descend from `contentRoot`; mark only title/close/template chrome as `baseChrome: true`.
   - **`branch: "FullScreen"` always ships its chrome.** Emit `baseChrome: true` containers mirroring `screen_template.prefab`'s `full_screen_template`: `top_view` (top-anchored: the screen title `text_title`, optional `button_info`) and `botview` (bottom-anchored: the template's `button_close` — the full-screen exit affordance, native size), plus a `Money_Bar` only when the screen shows currency. Read their real size/anchor from `ui-kit.json` / the prefab — never invent chrome sizes. Size `contentRoot: "content"` as the space between them, never over the chrome. A Popup's title + close come from `top_container_popup` (baseChrome) — never redraw them.
   - Use row/col/grid containers for ≥2 siblings; record exact size/gap/padding, grid `columns`/`cellSize`/optional `[x,y]` spacing, anchors/positions, font/color, and `childAlignment`. `stretch` anchors require `[left,right,top,bottom]` offsets. Omit an element size only when intentionally using its native UI-kit size. Every node with `parent` must also appear in that parent's `children`.
   - **Containers are invisible layout only — never style them visibly.** Do not put `background`, `border`, or `boxShadow` on a container (the validator rejects `container_style`). A visible panel / card / frame is an **element** using a frame template of the kit — base kit: `FrameTemplate` (plain frame) — anchored `stretch` as the first child of the container it frames; a framed block with a heading is a `section` container (below). The Popup outer frame + title bar come from the base-template chrome (mark them `baseChrome: true`); never redraw the popup background as a styled container. The `/new-ui` builder cannot turn a styled container into a real framed sprite — it emits a raw recoloured Image instead (a shipped defect).
   - **A scrolling area is a container flag, never an element.** When the stacked content is taller than the space it sits in (a long section list, a roster grid, a rules panel), set `"scroll": "vertical"` (or `"horizontal"`, or `"loop"` when the item count comes from CSV/runtime and needs `LoopListView2` recycling) on that container and give it the viewport `size` (or `stretch` + offsets). `/new-ui` then instantiates `ScrollViewTemplate` / `ScrollViewLoopTemplate` and drops the children into `Viewport/Content`. Never emit a scroll template in `elements[]` — elements hold no children, so the body would land outside the viewport (validator rejects it as `scroll_as_element`). Leaving the flag off is how the builder ends up hand-adding a raw `ScrollRect` to the base template.
   - **A tab strip is a container flag, never a hand-made row.** The kit's tab strip (base kit: `tab_template`, or `TabTogglerGroupBar`) owns the tab row — `ToggleGroup` + `HorizontalLayoutGroup` + `UI_TabExtensions`. When the screen has tabs that switch pages in the same screen, emit the strip as a `"tabBar": true` container of `type: "row"` inside the content, whose children are the strip's toggle elements (`toggle_tab_template` / `TabToggle_template_cell`), and give each tab its own page container next to it. Never put tab toggles in a plain row (validator rejects `tabs_outside_bottom_bar`) and never emit the strip template in `elements[]` when toggles exist (`tabbar_as_element`) — that is how a screen shipped a floating tab row while the controller hand-rolled `Toggle` listeners. A nav bar whose buttons each open another screen is a launcher, not a tab strip: plain buttons in a row, noted in `assumptions[]`. (Older project kits with a bottom tab bar in the full-screen chrome additionally warn `tabbar_in_content` / `tabbar_empty_chrome` — follow the kit's `usage` notes there.)
   - **A titled info block is a container flag, never a styled box plus a loose label.** When the screen stacks several blocks of content that each need a heading (rules / reward sections, stat groups), set `"section": {"title": "Luật chơi", "localize": "#key"}` on the container holding each block's body. `/new-ui` then builds it as the kit's titled frame (base kit: one `panel_template` instance — frame + its own `Title`). The frame must *wrap* the body, which elements cannot do — so never emit `panel_template` / `FrameTemplate` as children of a `section` container (validator rejects `section_frame_as_element`), and never fake the pattern with a background on the container plus a `text_head` heading above it. The title is a STATIC label — `localize` is `"#key"` or `"none"`, never `"dynamic"`. (Older kits whose title is a pill hanging above the frame also warn `section_padding_top` / `section_parent_gap` / `section_title_without_frame`.) Leaving the flag off is how a shipped screen became a flat wall of text.
   - **Never draw the cheat menu.** `CheatMenu` is dev-only chrome (hidden unless `GameSystems.isCheat`) that the `/new-ui` builder instantiates at the prefab root from the task's `[CHEAT]` list — not a design element. Emit no `CheatMenu`, no cheat buttons, and reserve no space for them.
   - **Prefer composite templates.** A top currency bar is `Money_Bar` (ships its `button_money_bar` chips), not hand-placed `ResourceViewer` chips. A currency that is a **new `EnumBase.MoneyTypes`** belongs *inside* that bar too — draw it as an extra chip and note in `assumptions[]` that the builder adds it to **this feature prefab's own `Money_Bar` instance** as an "Added GameObject" override (never editing the shared `Money_Bar_Template/Money_Bar.prefab`, which would push the chip onto every screen in the game); never draw a separate currency block next to the bar. Only drop to an individual `ResourceViewer` / `CurrencyPreview` for a resource that is **not** a `MoneyTypes` (feature-local state), and record that deviation in `assumptions[]`. Prices and requirements are `money_bar_require_view`; a pack is one `purchase_template`.
   - **Fixed-size chrome shares one size.** Timers (`cooldown_timer_template`, `OfferExpriesTimer_Template`), resource chips (`ResourceViewer`), currency (`CurrencyPreview`, `money_bar_require_view`) and badges (`notification_count`, `notification_dot`) reuse the template's native size; two instances at different sizes reads as uneven UI (the validator warns `inconsistent_chrome_size`).
   - Every non-empty text uses `localize: "#key"`, `"dynamic"`, or `"none"` for a visual glyph. Reuse localization keys before proposing new ones.
   - **Polish floors** (`.claude/docs/PolishRules.md` §9 — the validator blocks the measurable ones as `polish_*`; thresholds in `project-profile.json` → `polish`): every button carries `"role"` (`primary` / `secondary` / `ads` / `cancel` / `close` / `back` / `nav` / `tab` / `item` / `locked`) and the screen has **at most one** `primary` outside repeated lists (an info / list screen with no main action has none — never invent one); an action pair (primary + secondary / cancel / ads) sits in a `row`, secondary left, primary right — never stacked in a `col`; `fontSize` ≥ 32 (never < 30); every tappable ≥ 128 px on both axes — a smaller visual (an ⓘ, a chip) keeps its size and declares `"hitArea": [128, 128]` (template chrome marked `baseChrome` keeps its native size); primary CTA height 152–176 when the kit allows (soft); every gap / padding on the 4 px grid (4 / 8 / 12 / 16 / 24 / 32 / 48 / 64); full-width panels on the 6-column grid (6 × 150, gutter 24, margin 30) with ≥ 16 inner padding; no feature-added tappable in the top 100 px / bottom 60 px of the canvas (safe zone — template chrome exempt); text boxes sized for ~30 % longer translations, button labels one line; primary CTA in the lower half. Draw the states the screen has: locked = grey + a reason line ("Mở ở cấp 5"), not-enough-currency on the button itself, an empty list = image + one line. Ads buttons get the ads role (their own colour + ▶).
   - **Decide, don't ask — drafts are auto-approved.** After drafting, the pipeline freezes the mockup to its PNG contract with NO human round; every `questions[]` entry or literal `[?]` blocks that auto-approve and forces a dev detour through the dashboard. So make the best-supported call yourself and record it in `assumptions[]`. For values that bind at runtime (counts, prices, multipliers), use a representative sample value + `localize: "dynamic"` (e.g. `1.200`, `$4.99`, `×2`) — never a literal `[?]`.
   - The ONLY exception is a true forbidden-to-invent economy/reward value that the context docs do not contain AND that must appear as a fixed design decision (not a runtime bind): only then use `[?]` + a `questions[]` entry.
   - **Make discrete choices instant whenever possible.** Use `{"q":"...","options":[{"label":"4 slots","patch":[{"op":"replace","path":"/containers/@reward-grid/columns","value":4}]}, ...]}`. Patches support `add|remove|replace` and may target only `/containers`, `/elements`, `/wiring`, or `/assumptions`. Prefer stable `@<node-id>` selectors over numeric indexes. The dashboard hash-checks, applies all selected patches, removes answered questions, renders, and validates without AI. An empty `patch: []` accepts the current draft. Keep legacy string options only when a choice cannot be expressed safely as a deterministic patch; those choices use AI regenerate. Never fabricate the answer itself.
   - Record every non-obvious call you made in `assumptions[]` (what you read from CSV/GDD verbatim vs. what is an illustrative placeholder). Assumptions do NOT block auto-approve; they are the audit trail the dev reads when they later ask for edits.
3. Recover partial/idempotent output before drafting:
   - Both files exist → validate HTML and run renderer `--check`; return `exists` only if both pass. `--check` failing only because the HTML is stale (renderer or kit changed since — `rendered HTML is stale`) while the spec validates → re-render it from the spec (authoritative, deterministic) and return `recovered`.
   - Only `.ui-spec.json` exists → validate and render the missing HTML; return `recovered`.
   - Only `.html` exists → validate it as legacy and return `legacy-exists` (never invent a v1 sidecar).
   - Any failed check → return `error`; never report a pair complete when HTML is absent/stale.
4. When neither exists, write only `<Screen>.ui-spec.json`, then run:

```bash
python3 .claude/scripts/ui-spec-validator.py <Screen>.ui-spec.json --mode draft
python3 .claude/scripts/ui-spec-render.py <Screen>.ui-spec.json --output <Screen>.html
```

5. Return exactly one JSON object:

```json
{
  "status": "created | recovered | exists | legacy-exists",
  "specPath": "TechSpec/Mockups/<Feature>/<Screen>.ui-spec.json",
  "path": "TechSpec/Mockups/<Feature>/<Screen>.html",
  "elements": 7,
  "templatesUsed": ["button_template_CTA_txt", "ItemPreview"],
  "assumptions": [],
  "questions": [{"q": "4 ô gear (đổi nhãn) hay thêm ô Cung thứ 5?", "options": ["4 ô — đổi nhãn theo GDD", "5 ô — thêm ô Cung"]}]
}
```

On validation/render failure, return `status: error` with the command output. Do not approve, export PNG, edit task files, build galleries, or stage files.

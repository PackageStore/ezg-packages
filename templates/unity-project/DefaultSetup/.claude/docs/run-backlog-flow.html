Backlog Pipeline — từ ý tưởng đến push

Hệ thống có đúng 2 giai đoạn: dev lập kế hoạch bằng 2 lệnh tay, rồi loop tự thực thi từng task — code, qua 4 cổng chất lượng, commit, push — không cần người ngồi canh.

lệnh dev gọi tay thư mục backlog cổng chất lượng (tự sửa ×2 rồi mới chặn) hard-stop — dừng loop script tất định / không dừng loop
Chỉ chip đỏ dừng được loop. Mỗi cổng fail đều được tự sửa tối đa 2 round trước; DEFERRED (xanh) chỉ dời task xuống cuối hàng rồi chạy tiếp.
Skip ≠ block. Cổng thiếu điều kiện chạy (không Editor, worktree mode, diff chỉ .md/CSV) ghi skipped + lý do rồi đi tiếp — vì vậy manual-verify trong report luôn bắt buộc.
Subagent không bao giờ sửa code. Orchestrator là người viết duy nhất; reviewer/verifier chỉ đọc và ra verdict. Backlog nằm trong .git/backlog/ nên report cuối là bản giao duy nhất.

Giai đoạn 1 — Lập kế hoạch (dev gọi tay)

Hai lệnh duy nhất dev cần nhớ: /planning-task để tạo spec, /add-to-backlog để xếp hàng. Mọi thứ khác tự động.

BƯỚC 1/planning-task [ý định] parallel-safe — chạy nhiều cái cùng lúc được

Nhận một ý định bất kỳ và trả về một file spec trong backlog/planning/. Tự phân loại 3 nhánh:

  • Scaffold thuần khớp một workflow /new-* (feature, skill, enemy, UI, package, class) → ghi thin-spec workflow-backed với **Backed by workflow:** + **Workflow args:**. Không cần planner — tiết kiệm ~15–25K token. Lúc thực thi, loop chạy đúng workflow đó thay vì code tự do.
  • Task thường → triage tier XS / S / M / L. XS/S/M-đơn-giản: draft ngay tại chỗ. M-phức-tạp/L: spawn task-planner viết spec chi tiết. Task lai (scaffold + logic) vẫn workflow-backed, planner chỉ plan phần delta.
  • Input là cả GDD / design doc → không tự xử mà dispatch /planning-system (card dưới).

Filename <timestamp>-<TIER>-slug.md, timestamp lấy từ backlog-ops.py timestamp — vì vậy nhiều phiên planning chạy song song không đụng nhau, và không ai đụng vào BACKLOG.md.

BƯỚC 1+/planning-system — khi input là cả một hệ thống subagent per stage

Design-first: validate thiết kế trước, sinh task sau. Chuỗi stage: (gdd-final nếu economy chưa validated) → feature analysis → tech-spec (audit 4 lens, có quyền ABORT) → implementation mapping → batch-ground N task.

  • N task dùng MỘT timestamp chung + số thứ tự NN theo topo dependency — thứ tự promote chính là thứ tự thực thi.
  • Mỗi task mang **Context docs:** (trỏ TechSpec — số liệu economy/CSV lấy nguyên văn, cấm bịa), **Depends on:**, và **Requires:** unity-editor cho task UI.
  • Task UI sinh kèm mockup tự động: drafter vẽ wireframe từ UI-kit → auto-approve thành PNG 1080×1920 + spec JSON nhúng. Screen còn câu hỏi cấm-bịa ở lại PENDING-APPROVAL và bị chặn promote.
  • Pipeline chỉ dừng hỏi dev đúng 4 nhóm cấm-bịa: economy/reward · save-migration · backend/IAP/security · UX flow cốt lõi. Còn lại tự quyết.

BƯỚC 2/add-to-backlog — duyệt và xếp hàng backlog-ops.py promote

  • Liệt kê task trong planning/ → dev chọn 1 / nhiều / tất cả.
  • promote làm phần còn lại một cách tất định: gán số NNN, chuyển file planning/ → todo/, append bullet cuối hàng FIFO, warn nếu đứt Depends on, chặn nếu mockup còn PENDING-*, tự lint.
  • Priority chỉ là tag — không đổi thứ tự. Hàng đợi luôn là FIFO theo thời điểm promote.

NỀN TẢNGBacklog sống ở đâu và luật bất di bất dịch

  • Toàn bộ backlog nằm ngoài worktree: $(git rev-parse --git-common-dir)/backlog/ = <repo>/.git/backlog/. Per-dev, không commit, không merge được — nhưng mọi git worktree của cùng clone thấy chung một hàng đợi.
  • 4 thư mục = 4 trạng thái: planning/ → todo/ → in-progress/ → done/. Index là BACKLOG.md cùng chỗ.
  • Mọi transition đi qua backlog-ops.py — không hand-edit BACKLOG.md, không git add/mv file backlog. Hand-edit từng làm hỏng index thật.
  • Clone mới: chạy bash .claude/scripts/bootstrap.sh (Windows: bootstrap.ps1) — dựng link view cho provider + git + backlog trong một lệnh. Chỉ muốn riêng phần backlog thì python3 .claude/scripts/backlog-ops.py init.

NỀN TẢNGProject profile — vì sao doc viết <sourceRoot> chứ không viết đường dẫn

  • Hệ thống backlog/planning này ship nguyên xi sang mọi project, nên mọi thứ khác nhau giữa các project nằm trong một file dữ liệu: .claude/project-profile.json. SKILL.md không còn nhắc tên đường dẫn nào của riêng game này.
  • Vì vậy trong skill và trong trang này, placeholder ngoặc nhọn — <sourceRoot> · <featuresRoot> · <gameplayRoot> · <gitConfigPrefix> · <solutionFile> — phải tra ra giá trị thật trước khi dùng, đừng đoán theo hình dạng repo: 
    python3 .claude/scripts/project_profile.py            # tất cả key
python3 .claude/scripts/project_profile.py sourceRoot # một key
  • Thiếu file profile không phải lỗi — reader rơi về DEFAULTS dựng lại đúng hành vi cũ của repo này. Chính vì thế lớp gián tiếp này không thể làm đổi kết quả preflight ở đây.
  • Script tự đọc profile, không hard-code: cổng COMPILE tier 2 build project_profile.py solutionFile; preflight quyết định file nào là "sensitive" theo profile — backlog-preflight.py và bản twin .ps1 bị test_preflight_twin_parity.py ép chạy cùng một luật.

Giai đoạn 2 — Thực thi (tự động 100%)

Loop runner spawn mỗi task một cửa sổ terminal với context hoàn toàn mới, chạy /run-backlog trọn gói bên dưới, cửa sổ tự đóng khi xong. Orchestrator là người viết code duy nhất — subagent chỉ đọc và ra verdict.

1PICK backlog-ops.py pick

  • Lấy task đầu hàng TODO — không chọn lọc, không ưu tiên. Task in-progress dở dang → resume, nhảy thẳng bước 4.
  • Exit 2 = hàng rỗng → ghi PAUSED, loop dừng. Exit 3 = chưa init → init rồi pick lại.
  • Task có **Requires:** unity-editor → probe Editor, retry ~4 lần/20s (một lần im lặng có thể chỉ là domain-reload). Editor chết: còn task headless khác → defer task này xuống cuối hàng và loop chạy tiếp; mọi task đều cần Editor → EDITOR_REQUIRED, dừng.

2–4CHUẨN BỊ — branch · start · context

  • Branch: mode current (mặc định) bỏ qua hẳn — không checkout, không merge, commit thẳng nhánh dev đang mở (checkout giữa chừng bắt Unity reimport cả project). Mode worktree: merge origin/<base> vào agent/dev-<base>; xung đột → BASE_MERGE_CONFLICT, không tự resolve.
  • Start: backlog-ops.py start NNN — todo → in-progress trong một lệnh.
  • Context: probe CodeGraph một lần quyết định cách tra code cho cả task; đọc rules + SKILL.md liên quan; task batch đọc Context docs — số liệu lấy nguyên văn từ TechSpec.

5IMPLEMENT

  • Task workflow-backed → đọc .claude/commands/<name>.md, thực thi inline + áp Custom delta. Task thường → code theo convention: FeatureBaseController · UIManager · TimeManager · UniTask · DataPlayer + SetupDefaultData() · TigerForge · DOTween SetUpdate(true) · localize toàn bộ text.
  • Xong: git add -A, chưa commit — cả 4 cổng soi trên staged diff.

CỔNG 1COMPILE ↻ tự sửa ×2 · worktree: skip

  • 3 tier, dừng ở tier đầu tiên chạy được: Unity MCP (instant) → dotnet build (~10–40s) → Unity batchmode (~60–180s).
  • Còn lỗi sau 2 round sửa → COMPILE_BLOCKED.

CỔNG 2REVIEW preflight code perf? security? ↻ ×2

  • Preflight tất định chạy trước (miễn phí, bắt DateTime.Now, coroutine mới, PlayerPrefs, direct Supabase write, credential…): diff rỗng → NO_CHANGES; critical không sửa nổi → PREFLIGHT_BLOCKED.
  • Rồi spawn reviewer song song, theo tier (xem tab Tra cứu): code-reviewer luôn (trừ XS) · performance-reviewer nếu diff chạm hot-path (Update/Instantiate/LINQ/pool/LoopListView2) · security-auditor nếu $SENSITIVE (Backend*/Purchase*/IAP*/Auth*/Leaderboard*/AntiCheat*, credential, ghi currency qua RewardManager — save tiến độ thuần không tính).
  • Reviewer chặn → tự sửa ×2 → còn chặn = REVIEW_BLOCKED.

CỔNG 3VERIFY qa-verifier chỉ M/L · ↻ ×2

  • Đối chiếu từng dòng "Tiêu chí hoàn thành" trong spec với diff — đúng convention chưa đủ, phải đúng yêu cầu; không tiêu chí nào được lặng lẽ bỏ qua. Xuất manual_verify_steps cho dev.
  • Fail sau 2 round → VERIFY_BLOCKED. Cuối bước: preflight chốt lần cuối. XS/S bỏ cổng này (manual-verify lấy thẳng từ spec).

CỔNG 4SMOKE chỉ M/L + Editor sống · ↻ ×2

  • Cổng duy nhất chạy game thật: console clear → play mode → boot ~20–30s → acceptance recipe (dùng Cheat_* nếu có) → đọc console → screenshot → thoát.
  • $SENSITIVE → invariant suite: currency net-zero · save/load roundtrip · reset đúng scope.
  • Exception/error xuất phát từ đúng code trong diff → FAIL → sửa ×2 → RUNTIME_BLOCKED. Thiếu điều kiện chạy (worktree, không MCP, diff chỉ .md/CSV, Editor treo) → skip có lý do, không bao giờ là block.

8–10DONE → SHIP → REPORT backlog-ops.py done · lint

  • DONE: script chuyển in-progress → done; orchestrator viết summary: fix summary, verdict từng cổng, mode, manual_verify_steps y nguyên.
  • SHIP: commit + git push thẳng nhánh làm việc. Không tạo PR. Backlog nằm trong .git/ nên không dính commit.
  • REPORT: bản giao duy nhất cho dev (DONE summary không theo commit): file đã đổi, commit, verdict + số round mỗi cổng, và MANUAL VERIFY REMINDER đánh số — worktree mode thì bước 1 luôn là /compile-check.
  • Xong → cửa sổ đóng → loop lấy task kế tiếp với context mới. Task blocked giữa chừng → demote về đầu TODO.

Chạy loop

# macOS / Linux — mỗi task 1 cửa sổ Terminal, tự đóng khi xong
bash .claude/scripts/run-backlog-loop.sh --auto-model-by-tier               # mode current
bash .claude/scripts/run-backlog-loop.sh --auto-model-by-tier --mode worktree

# Windows
powershell -ExecutionPolicy Bypass -File .claude/scripts/run-backlog-loop.ps1 -Mode Current

# Bookkeeping / debug
python3 .claude/scripts/backlog-ops.py lint          # check index ↔ thư mục
python3 .claude/scripts/backlog-preflight.py -Pretty # chạy preflight tay trên staged diff
python3 -m unittest discover -s .claude/scripts/tests # regression test trước khi sửa 2 script trên

--auto-model-by-tier: XS/S → sonnet, M/L → opus. Base branch = nhánh hiện tại lúc bắt đầu, lưu vào git config <gitConfigPrefix>.agentBaseBranch; đổi base bằng git config --unset rồi chạy lại từ nhánh mới.

Flow tổng — một cửa vào, cascade phân loại

Ba cổng quyết định chạy theo đúng thứ tự ưu tiên: 0b (new-system) trước 0a (workflow-backed) trước tier triage. Cổng đầu tiên khớp sẽ chốt case.

/planning-task <intent | doc>
STEP 0b NEW-SYSTEM?

Fire khi CẢ HAI: (1) doc-scale — cả GDD nhiều section, HOẶC ≥2 module MỚI tương tác nhau; (2) KHÔNG gói được thành 1 task workflow-backed. Chạm economy đơn thuần không kích 0b — chỉ là tín hiệu tier.

CÓ →

Intent scaffold thuần khớp một /new-* trong registry (/new-feature, /new-skill, /new-package…).

MATCH →
CASE B WF pure — scaffold thuần
CASE C Hybrid — scaffold + delta → vẫn qua tier triage

Không match workflow (hoặc HYBRID: 0a match + delta logic — vẫn phải qua cổng này) → phân theo độ phức tạp & blast-radius. Phân vân giữa 2 tier → chọn tier LỚN hơn: gate review của run-backlog key theo tier và không tự escalate lúc thực thi — tier thấp oan = bỏ qua reviewer oan.

03

Case A chi tiết — /planning-system

Orchestrator design-first cho hệ thống mới lớn. Năm giai đoạn, tự co giãn theo profile chọn ở INTAKE; resume bằng --from-mapping (vào thẳng [2] PLAN). Sơ đồ nhánh nội bộ đầy đủ: tab Diagram → Sơ đồ 2.

[0]
INTAKE
FeatureName, PROFILE detection, idempotency probe, guards.
[1]
DESIGN
Subagent per stage, chạy theo profile; mỗi stage trả OK / QUESTIONS / ABORT (+ profile_escalation).
[2]
PLAN
Parse mapping §10.1–10.7 (EPIC: merge) → existence probe → route + gán exec tier per item (pure-WF / HYBRID / UI) → ownership map + topo order.
[3]
GROUND
1 batch timestamp + NN index → task-planner (HYBRID) + mockup-drafter (UI) fan-out ≤10/wave → tự viết N file → git add.
[4]
REPORT
Profile + bảng task + promote order + câu hỏi/giả định.

Ba profile — pipeline tự co giãn

LITE
Khi: Không economy/monetization/competitive/backend-write VÀ ≤5 sub-feature (tutorial, photo mode).
Bỏ hẳn 03-gdd-final; 05 bắt buộc 2 lens (Flow + Feasibility) — Lens 2/4 chỉ chạy khi spec lộ surface tương ứng; không simulation — cắt ~40–60% token design.
04 → 05(trim) → 06
STANDARD
Khi: Có economy/monetization HOẶC 6–15 sub-feature. Mặc định khi thiếu tín hiệu.
Flow đầy đủ 4 lens audit.
(03?) → 04 → 05 → 06
EPIC
Khi: Backend write/PvP/social/guild HOẶC >15 sub-feature HOẶC nhiều bounded context.
04 xuất Module Split Plan → 05+06 chạy per-module theo build order → merge dependency graph; 05 thêm API Contract & Server Authority (bắt buộc khi có backend write).
(03?) → 04+Gate → per-module 05→06

Stage được phép báo profile_escalation khi phát hiện profile sai (vd LITE lộ economy) → orchestrator nâng profile, chạy bổ sung stage thiếu — không làm lại từ đầu, không bao giờ tự hạ. Tương tự, 05 ở STANDARD gặp scope quá lớn trả ABORT: suggest EPIC split → nâng EPIC + chạy lại từ Decomposition Gate của 04 thay vì dừng hẳn.

Đặc điểm batch output

NN
Một timestamp chung cho cả batch + NN = thứ tự topo từ Dependency Graph → promote sort (timestamp, index) nên NN chính là thứ tự thực thi.
↳
Mỗi task mang Context docs (trỏ TechSpec — không bịa lại số liệu), Depends on (promote warn khi đứt); riêng UI task thêm Requires: unity-editor + groundTruth= (mockup pipeline — xem §04).
TIER
Batch trộn nhiều tier: pure-WF lấy exec tier theo registry (thường M, L nếu save + cross-system), HYBRID M/L, UI S–M. Tier từng task lái review-gate run-backlog + --auto-model-by-tier (XS/S → sonnet, M/L → opus).
UI
UI screen tách thành task /new-ui riêng, xếp cuối batch; task /new-feature tương ứng skip step prefab.
L10n
Localize không bao giờ là task riêng (không tạo git diff → NO_CHANGES) — fold vào task feature sở hữu string.
04

Mockup pipeline — UI ground truth

Task /new-ui không build từ mô tả text — nó cần ground truth hình ảnh (new-ui-guide §0a). Nguyên tắc xuyên suốt: generate = autonomous (parallel-safe) · approve = human (serial, bất đồng bộ) — duyệt visual là quyết định gu con người nhưng KHÔNG dừng planning.

GENERATE · autonomous
planning (N phiên song song, parallel-safe)
Phát hiện task UI → spawn mockup-drafter per screen → đọc .claude/ui-kit/ → ghi <S>.ui-spec.json rồi generate <S>.html — chỉ ghi pair của screen, không UI Review Dashboard, không shared state → task vẫn nhận groundTruth=PENDING-APPROVAL:<html>.
APPROVE · human
/ui-mockup (MỘT phiên interactive, lúc nào tiện)
grep PENDING-* trong backlog/planning/ → draft nốt phần thiếu (PENDING-MOCKUP) → mở static UI Review Dashboard → button gọi claude-cli://open tại project với prompt hash-bound → validate + export PNG 1080×1920 → regenerate dashboard bỏ card approved → flip groundTruth=<png> → git add (KHÔNG commit).

05

Khi nào hệ thống DỪNG HỎI user

Chỉ đúng 5 nhóm dưới đây — mọi thứ khác tự quyết + ghi assumption. Đây là ranh giới “cấm bịa”.

1Economy / reward — giá IAP, số lượng, tỉ lệ drop
2Save data — migration, persist-restart
3Backend / auth / IAP / security — leaderboard
4UX flow — product behavior cốt lõi
5Acceptance criteria / verify steps bị mơ hồ
Quy tắc

Docs đầu vào đã chốt đủ số liệu = chạy 0 câu hỏi full auto tới N task.

Giá trị thiếu thuộc nhóm cấm = marker [DECISION NEEDED] + câu hỏi — không bao giờ tự bịa.

Riêng duyệt mockup UI (visual composition — nhóm cấm-bịa thứ 5, mở rộng của nhóm 4): xử lý bất đồng bộ, KHÔNG dừng pipeline — generate tự động lúc planning, approve gom một phiên ở /ui-mockup.

07

Điểm dễ nhầm

Năm cặp khái niệm hay bị lẫn — mỗi cái là một “không phải”.

“Tạo 1 package IAP” không phải new-system

0b nhường 0a → thành CASE B (WF pure, tier M, sensitive), không kéo cả pipeline thiết kế ra. Chạm economy chỉ là tín hiệu auto-bump tier, không phải tín hiệu new-system.

WF không phải tier

Task workflow-backed vẫn mang exec tier thật (XS/S/M/L) trong filename. Tier quyết định review-gating của run-backlog (code-reviewer, qa-verifier); riêng security-auditor spawn theo $SENSITIVE của diff — bất kể tier, XS/S chạm Purchase*/Auth*/value-bearing vẫn bị audit. WF chỉ quyết định “load workflow trước khi implement”.

Profile không phải tier

Hai trục co giãn độc lập: profile (LITE/STANDARD/EPIC) scale độ sâu pipeline thiết kế của cả hệ thống (chỉ Case A); tier (XS/S/M/L) scale độ sâu spec + review-gate của từng task. Hệ thống EPIC vẫn đẻ ra task S; batch nào cũng trộn nhiều tier.

Batch mode không đệ quy

Khi /planning-system tái sử dụng drafting path của planning-task (flag origin: planning-system), STEP 0b/0a-dispatch bị tắt hoàn toàn. Depth cap = 1.

Priority là tag, không phải thứ tự

Queue chạy theo FIFO/task-order (timestamp + NN), không reorder theo HIGH/MEDIUM/LOW. Priority chỉ là nhãn.
